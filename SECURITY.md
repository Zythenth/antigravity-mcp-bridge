# Security policy

Security fixes target the latest published version of the plugin. Update the plugin and the official CLI before reproducing a problem.

## Reporting a vulnerability

Use [Report a vulnerability](https://github.com/Zythenth/black-gravity/security/advisories/new) to send a private report to the maintainer. The private vulnerability channel is enabled in the repository. Include the bridge and `agy` versions, the operating system, minimal steps, expected behavior, and observed impact. Remove tokens, personal data, and sensitive content from examples. Do not publish exploitation details in public issues while the problem is under analysis.

## Controls and limits

- Execution over local stdio, with no HTTP server or network port opened by the bridge.
- Subprocesses without a shell. Discovery (`discover`) of the official CLI requires exit code 0 on `--version` and `--help`, non-empty output, and proven support for `stream-json` and `--sandbox`. Structured diagnostics distinguish `AGY_NOT_FOUND`, `AGY_PERMISSION_DENIED`, `AGY_PROBE_FAILED`, `AGY_INCOMPATIBLE`, `CLI_INPUT_FAILED` (closed stdin, EPIPE, EOF), `AGY_IO_FAILED`, and `AGY_PROCESS_FAILED`.
- The Anti-AI Craft snapshot is verified by manifest before each new task and copied to a private per-revision directory with atomic promotion. Under a tool policy, hooks allow only `read_file` and `view_file` in that root; writes and other paths outside the copy remain denied. Without a tool policy, the root has no operating system write protection; the next task detects tampering through the manifest and recreates the copy.
- Cancellation and timeouts (`TASK_CANCELLED`, `TASK_TIMEOUT`): the first recorded intent prevails, triggering termination of the process and descendants, with no perfect guarantee for processes that escape the process group or operating system permissions. Error messages from external tools may contain unknown secrets; the bridge applies redaction to known error forms and patterns and its operations do not add credential values to logs or pass tokens as arguments, without promising absolute absence.
- At the end of each CLI run, even on success, the bridge observes again the processes belonging to the run and records `processCleanup`. On Windows, the tree is rebuilt by parent PID and creation time from the moment of the spawn, which excludes reused PIDs; each process is terminated and its absence is confirmed within 3 s. On POSIX, the run's own process group is terminated and its absence is confirmed. When confirmation fails, `processCleanup.verified` stays `false` and resumes, tests, integrations, and messages for that copy are refused with `PROCESS_CLEANUP_UNVERIFIED` until a new observation confirms termination. Limit: on Windows, descendants whose intermediate process has already ended cannot be associated by parent PID and are not part of the verification.
- CLI environment isolated through `cliEnvironment`, forwarding only essential system, user, locale, proxy, certificate, and official authentication variables. Adding other variables is strictly opt-in through `BRIDGE_ALLOWED_ENV_VARS` (e.g., `["MY_TOOL_SETTING"]`, injection not being the default; JSON array, case-insensitive on Windows, exact on Unix). Runtime injection variables (`NODE_OPTIONS`, `NODE_PATH`) and dynamic namespaces (`LD_*`, `DYLD_*`) are strictly blocked from opt-in in `loadConfig` and in direct calls to `cliEnvironment` on any platform (including mixed casing and whitespace); the refusal emits diagnostics naming the variable without exposing values. `NODE_EXTRA_CA_CERTS` and default variables are preserved. Third-party credentials (AWS, GitHub, OpenAI, Stripe) and local agents (`SSH_AUTH_SOCK`, `GPG_AGENT_INFO`) remain omitted by default.
- Official authentication kept in `agy` through native credential managers (Windows Credential Manager, macOS Keychain, Linux Secret Service via D-Bus), preserving `GEMINI_API_KEY`, `GOOGLE_GEMINI_BASE_URL`, certificates, and proxies. ADC/Enterprise variables are preserved for compatibility (Enterprise flow not validated end to end). Primary documentation in [Antigravity CLI installation](https://www.antigravity.google/docs/cli/install/).
- Preventive secret preflight run AFTER Git exclusions and `includePaths`, and BEFORE the temporary copy. It blocks `.env`, `.env.local`, and other `.env.*` variants (except `.env.example`, `.env.sample`, `.env.template`, and `.env.dist`, which remain under content analysis), `.envrc`, private keys, keystores, known authentication files, and high-confidence credential patterns by content. Certificates, public keys, and synthetic fixtures remain allowed.
- Secret exclusions (`BRIDGE_SECRET_EXCLUSIONS`, JSON array) and exceptions (`BRIDGE_SECRET_EXCEPTIONS` and runtime `ProjectLimits.secretExceptions`, strict versioned object `{"version": 2, "namePatterns": [...]}`) with support for relative paths and `*`, `?`, `**` globs, without traversal (`..`), without NUL, and without absolute paths. Non-empty legacy arrays fail with a diagnostic guiding the migration without exposing secret values; empty arrays or omission normalize to an empty policy. Explicit v2 exceptions skip only the credential name block (`SECRET_FILE`); all allowed content remains under strict content inspection (`SECRET_CONTENT`). Strict precedence: Git ignores and unsafe paths (`UNSAFE_PATH`) ALWAYS win; an explicit deny beats exceptions; v2 exceptions skip only `SECRET_FILE`. The preflight does not guarantee detecting arbitrary secrets in code, unknown formats, or encrypted data.
- `blockedFiles` reporting in the `copy.ready` event, containing only `path` and `reason` (`SECRET_FILE`, `SECRET_CONTENT`, `SECRET_EXCLUSION`, `UNSAFE_PATH`), never exposing file content.
- Previews inspect the candidates and form a staging of verified bytes before generating patches, restoring the private index with `read-tree HEAD`. Per-file patch reading (`readProjectPatch`) extracts the corresponding slice directly from the verified and reviewed patch (`preview.patch`), strictly bound to the same SHA-256 hash without unsafe rereading of the shared index or the copy. Snapshots and fingerprints omit blocked generated files and reject a contaminated baseline. Artifacts reapply the secret policy and verify identity, size, and SHA-256 before responding. These protections do not remove preexisting Git objects nor guarantee eliminating all filesystem races.
- File and byte limits are respected in the scan and the copy; identity, size, or hash changes fail with `SOURCE_CHANGED` or `CONTEXT_CHANGED`, and the copy does not silently omit baselines that became credentials. Delegated tasks require `agy --sandbox`; tests use the bridge's own AppContainer/LPAC on Windows by default and the official `agy` sandbox on other systems.
- Query mode with `agy --mode plan` and later verification of the copy.
- Review by patch/hash and refusal of integration when the affected files in the source have changed. Text patches must preserve their bytes in the UTF-8 round trip; non-UTF-8 content requires a Git binary patch, obtained with `.gitattributes binary`, or fails with `UNSUPPORTED_PATCH_ENCODING`. Write runs over a copy with such files are refused before the CLI starts, with `UNSUPPORTED_TEXT_ENCODING`.
- Local Git operations require version 2.32 or later and use their own environment, without credentials, proxies, or injection variables. `PATH` contains only absolute directories outside the source and the copy. `core.fsmonitor=false`, disabled hooks, and blocking of configuration overrides prevent execution through those options; global/system configurations are isolated and ignore rules are preserved. The shared helper limits stdout to 10,000,000 bytes, stderr to 4,000 characters, and each operation to approximately 120 s, with redacted diagnostics and explicit truncation. When subprocess termination does not complete within the bounded tolerance window (retained pipes), the operation rejects with `GIT_CLEANUP_UNVERIFIED` and destroys stdio without assuming success or tree cleanup; affected copies receive a persistent refusal marker (fence) in the private baseline that prevents reuse, preview, tests, integration, artifact reading, or unsafe discard of retained copies, recording the cleanup uncertainty without claims of a perfect guarantee. Patch application uses the private baseline's configuration and a fixed whitespace policy, preserving the approved bytes without running the source's local filters. Forks use native commands and verify baseline tree equality, without depending on a POSIX shell.
- Configurable approval modes through `BRIDGE_APPROVAL_MODE`: default `auto` when not defined (unset), with strictly accepted values `auto` or `ask`. In `auto` mode, the integration of verified patches (`black_gravity_integrate`) and validated sandbox policy updates (`black_gravity_set_sandbox_policy`) are authorized automatically, waiving interactive MCP human confirmation forms and imposing no extra manual confirmations on the caller. In `ask` mode (strict opt-in), integration and sandbox updates ALWAYS require human confirmation through an MCP form (**MCP form elicitation**), even for previously configured or remembered legacy roots; the remember checkbox in the form has been removed. In both modes, validation of the current SHA-256 hash, acceptance criteria approved through `black_gravity_verify`, technical review backed by the real files, current observed tests without failures, source-lock, CAS, and strict path protection (path-protection) remain rigorously mandatory.
- Local persistence with atomic writes and locks to protect operations on the same copy. `StateStore` has no generic support for cloud storage. In synced environments such as OneDrive, extra or transient link counts (`nlink`) are tolerated exclusively when reading assets with a trusted descriptor and pinned size and SHA-256, in the staging of the portable Node source with `expectedSha256`, and in the portable Node preparation lock (preserving identical `device`, `inode`, and `size` with verification of the exact nonce/payload, releasing with `unlink` only the process's own entry to preserve aliases). Hash, size, file identity, reparse marks, and directory layout remain strictly mandatory; altered content is refused and aliases are not modified. Runtime destinations, generic executables, and ACL grants still require a strict single link.
- Criteria defined before the task, review with checked citations, and mandatory verification before/after approval.
- Tests with an exact command, limited output, exit code, and before/after fingerprints. On Windows, the executor uses a new LPAC profile and ACL grants for the run's exclusive SID; elsewhere, the legacy path checks the `agy` receipt. There is no direct host execution as an alternative.
- On Windows LPAC, preparing Git discovered in `PATH` for Node/npm tests and direct git commands resolves `cmd` and `bin` launchers to the native binary in `ucrt64/bin` or `mingw64/bin`, preserving native executables and standalone installations and refusing known invalid or unsafe layouts, and copies only PE binaries, DLLs, and public helpers to a read-only single-link runtime, without granting ACLs or authorizations to the original installation. The isolated environment restricts `PATH` to the prepared runtime and the exact `System32`, points `GIT_EXEC_PATH` to the directory in the runtime alias, isolates the configuration (`GIT_CONFIG_NOSYSTEM=1`, `GIT_TERMINAL_PROMPT=0`, and a global file absent in scratch), and does not inherit `.gitconfig`, credentials, or keys. `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*`, `GIT_CONFIG_VALUE_*`, and `GIT_CONFIG_PARAMETERS` entries are removed, and the protected command configuration defines `safe.directory` restricted solely to the exact list of verified repositories present in the copy at the start of the run: an empty reset (`VALUE_0=''`), the root of the verified copy alias (`VALUE_1`), and the roots of descendant repositories with a verified `.git` directory inside the copy (`VALUE_2..N`), with no `*` wildcard and no trust outside the copy; new repositories created after admission remain subject to normal Git checks. New temporary repositories use isolated `GIT_DEFAULT_REF_FORMAT=reftable` (without converting existing repositories, without changing the host, and with a known limitation on the files backend without new metadata grants or UAC, keeping private parent directories denied). Git is not downloaded, its files count toward the mandatory copy limits, and its optional absence neither prevents Node/npm tests without Git nor authorizes host fallback or network widening.
- When Git is prepared, the Null device is queried by handle at the fixed path `\\?\GLOBALROOT\Device\Null`. The default rule `S-1-15-2-2`, when applicable, avoids any ACL write. If needed and allowed by the current token, the only grant added is a non-inheriting ACE of `0x12019f` for the run's exclusive SID. The DACL update is serialized across controllers; other rules are preserved and no elevation is requested.
- v3 leases record the intent before the ACL change and the Job creation before the subprocess. The Job has a nonce-derived name and a private ACL; its active process count must reach zero before cleanup. Recovery checks the controller and the Job, removes only its own ACE, and preserves leases when it cannot prove cleanup. v1/v2 leases keep legacy recovery. The SID is persisted right after profile creation; a failure without a SID does not turn the `creating` phase into an invalid cleanup lease.

Admission still refuses hardlinks and unsafe links in granted targets. Revocation revalidates the identity of the original target and can reconcile hardlinks or a final reparse point that appeared during the run. That reparse point is treated as a leaf: its ACL is reconciled without traversing the target, and unsafe ancestor components remain forbidden. Cleanup uses its own ceiling of 1,000,000 entries per tree, independent of the admission limit, and aggregates failures without abandoning siblings over an individual ACL error. Exceeding the ceiling or failing to prove reconciliation keeps the lease and blocks execution; there is no promise of unlimited or instant cleanup.

In Windows tests, the global policy limits read/write roots, network, child processes, and output. In `auto` mode (default if unset), validated global sandbox ceiling proposals are applied automatically without a form; in `ask` mode, the change requires human confirmation through an MCP form with comparison of the previous hash. The agent calling the MCP, whether Codex or another client, chooses narrow and verified grants needed per test within those authorized limits. The Gemini delegated through `agy` does not receive, choose, authorize, or change this configuration or sandbox grants. Source paths, bridge state, credentials, storage, links, aliases, and controlled temporaries cannot receive extra grants. There is no automatic fallback to the host, nor any change to the permissions of Codex or agy.

`network: true` enables only client Internet and bidirectional private LAN. It does not enable arbitrary capabilities, a localhost exception, or a firewall change. Updating the policy reaches new tests and queued tests after confirmation; it does not revoke permissions of processes that are already active.

An ACL is granted to the profile's exclusive SID and removed exactly at cleanup; if that cleanup fails, the bridge blocks execution and does not consider the test verified. An abrupt interruption or power loss can leave resources until later recovery, so there is no claim of instant cleanup or of complete operating system protection. The executor also uses temporary two-level DOS aliases for its copy, runtime, and scratch directories: it requires three free letters from `D:` to `Z:`, checks identity and removal, and the names are visible only in the current logon. They give no access to the volume root, are not persistent mounts, and do not require UAC. `plan` remains not a physical write barrier. For untrusted projects or sensitive documents, use a separate account or environment and check the limits before delegating.

There is a known Node compatibility limitation in LPAC: on Node 24.14.1/libuv 1.51, default `child_process.spawnSync` pipes use global endpoints refused by LPAC, and the execution expires with exit code 124. Children with inherited stdio and the real npm cycle having passed do not prove this general case. [libuv PR 5181](https://github.com/libuv/libuv/pull/5181/files), included in [libuv 1.53](https://github.com/libuv/libuv/releases/tag/v1.53.0), fixes this class of pipes. The portable runtime Node 24.21.0 LPAC1 Windows x64, with base libuv 1.52.1 and only that PR applied, is published in an immutable Release and passed the LPAC regression with captured default pipes. This validation applies to that pinned build. Therefore, Node 24 or later remains a server requirement, without guaranteeing all Windows LPAC tests; a timeout is a failure, not evidence for integration.

The portable runtime is prepared only by an explicit trusted initialization call. It accepts only the embedded descriptor, downloads `node.exe`, the upstream `LICENSE`, and `build.json` declared in the GitHub Release, checks size and SHA-256, and installs the cache atomically. The metadata records the source, the patch, and the build provenance for maintenance and auditing. Status, health, and tests do not start a download. A missing cache in portable mode requires `--prepare-windows-runtime`, with no fallback to the system Node. A corrupted, altered, or unsafe cache is also refused by preparation, with no automatic repair or removal. To prepare again, a person must inspect the path and manually remove only the cache of the affected build before running `--prepare-windows-runtime`. The cache can be shared only through the trusted `BRIDGE_WINDOWS_NODE_CACHE_DIRECTORY` environment; URL, hash, and path are not MCP parameters. The replacement applies exclusively to the exact identity of the known `process.execPath` and to the validated adjacent `npm`, without reclassifying custom executables. The initial portable replacement of `process.execPath` and the adjacent `npm` requires Node 24 on the server host. The general Node >=24 requirement allows starting the server, but Node 25/26 hosts fail eligible tests with `PORTABLE_NODE_HOST_UNSUPPORTED`.

The cache must stay outside projects. The bridge resolves the real paths and refuses overlap in both directions between the project and `BRIDGE_WINDOWS_NODE_CACHE_DIRECTORY` before querying models, queuing the task, or copying files, even with `includePaths` or in `system` mode.

In `ask` mode, integration confirmation necessarily depends on a trusted MCP client that presents the form to the user and sends their response (with no bypass for remembered or preauthorized roots). The bridge requires this exchange in the protocol and does not accept approval as a tool argument; it does not authenticate a named person or protect against a malicious client or programs with the same local permissions. `BRIDGE_APPROVAL_MODE` settings must be defined in the MCP server's private startup environment (example assignments in PowerShell affect only the current running shell), and the connection must be restarted after any change. Integrations are performed strictly through MCP without waiving tests and technical review.

Keep the state directory private and outside versioned projects. It contains prompts, results, events, policy, and recovery information without its own encryption. Ignore rules do not protect secrets sent directly in the prompt. Tests recorded by the client are reports. Untrusted model output is not a receipt. The executor's evidence proves only the observed limits and results; the bridge does not attest to the semantic correctness of the review opinion.
