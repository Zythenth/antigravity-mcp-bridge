# Waiting and delivery

Reference for the [core skill](../SKILL.md). Open it when waiting through MCP tools, or dealing with `truncated` losses, exit codes, multi-task or group waits, `continuationTaskId`, `deliveryMode: "events"` or a delivery mode change.

Keep the `taskId` and the `waitCommand` (`{ argv, sh, recommendedMode, reason }`) returned by `black_gravity_run`, `black_gravity_resume`, `black_gravity_handoff`, `black_gravity_compare`, `black_gravity_group_start` or `black_gravity_wait_many`. Follow `waitCommand.recommendedMode` strictly:
   - When `waitCommand.recommendedMode === "background"` (`reason: "verified-profile"`): ONLY Claude Code >= 2.1.310 is verified for background execution. Start `waitCommand.argv` (or `waitCommand.sh` in a POSIX shell) in the background right after delegating, and do not call `black_gravity_wait`, `black_gravity_wait_many`, `black_gravity_group_wait`, `black_gravity_status`, `black_gravity_group_status` or `black_gravity_events` while it runs. For background execution where supported (such as the host's `Bash` tool with `run_in_background: true`), explicitly check the real background deadline in the local host tool schema or configuration rather than inferring from foreground limits, as limits vary by mode and schema (do not assert a universal limit, change the global environment, or confuse the foreground maximum with background). Pass an explicit `timeout` in the Bash call (in milliseconds) and pass `--timeout` to the CLI `wait` command (in seconds) strictly below the host's real background deadline with a safety margin, ensuring the command process can emit its single JSON line before being killed by the host. A numerical example is only permitted conditionally on a confirmed host background deadline: for example, if a background deadline of 600,000 ms is confirmed, pass Bash `timeout: 600000` with `run_in_background: true` and append `--timeout 540` to the returned `argv`/`sh`; if the host imposes no background deadline, the product default of 1800s is preserved; do not alter the product default timeout.
   - When `waitCommand.recommendedMode === "foreground"` (`unknown-client`, `version-below-minimum`, `invalid-client-version` or `missing-client-info`): Codex, Copilot CLI, VS Code, agy, Cursor, Gemini CLI and any other hosts without proof are unverified for background; do not promise notifications or assume background capability in them, and do not add new profiles. If an exception by explicit tool capability is described or chosen, that choice must be reported as unverified. When a terminal is available in the host environment, ALWAYS prefer running `waitCommand.argv` (or `waitCommand.sh`) in the foreground (blocking) instead of 60-second MCP polling; use MCP wait polling (`black_gravity_wait` with `timeoutSeconds: 60`) ONLY as a fallback when the host cannot run terminal commands. For foreground execution, explicitly pass `--timeout` strictly less than the host terminal's real execution deadline, with a safety margin (e.g., if the host terminal has a known timeout limit such as 600s, set `--timeout` strictly below that limit with a margin, such as `--timeout 540`; a numerical example is only permitted conditionally on a known host terminal limit; if the host terminal imposes no deadline, the product default of 1800s is preserved; do not alter the product default timeout).
   - The `wait` command accepts single mode (`<taskId> [--after <n>]`), multi mode (1 to 32 `<taskId>` or `<taskId>:<after>`) and group mode (`--group <groupId>` with 0 to 32 `<taskId>:<after>` seeds); it only reads durable state, never writes or locks anything, and stopping it cancels no task or group (exit codes: `0` `completed`, `1` `error`, `2` `failed`, `3` `cancelled`, `4` `timeout`, `5` `question`, `6` `blocker`, `7` `unknown-task`, `8` `wait-deadline`, `9` `owner-stopped`, `10` `unknown-group`, `11` `group-paused`, `12` `group-ended`).
   - When the command ends, read the JSON line (single mode: `{taskId, outcome, exitCode, status, reason, after, cursor[, continuationTaskId]}`; multi/group mode: `{taskId, groupId, outcome, exitCode, status, groupState, reason, after, cursor, targets: [{taskId, nodeKey?, status, after, resumeAfter, cursor, continuationTaskId?}]}`) and make ONE single query according to `outcome`: terminal outcome (`completed`, `failed`, `cancelled`, `timeout`) -> one `black_gravity_result` with `includeResult: false` (or `black_gravity_comparison` / `black_gravity_group_status`); `question` or `blocker` -> one `black_gravity_wait` on the causing task (`taskId`) with `after: cursor - 1` (the first message returned is the question or blocker; earlier ordinary messages, if needed, follow through `nextCursor` from `after`), answer it and restart the command advancing the cursor with `--after <cursor>` (single mode) or passing `<taskId>:<resumeAfter>` from each `targets` item (multi/group mode), since the question/blocker was read and answered; `group-paused` or `group-ended` -> one `black_gravity_group_status`; `wait-deadline` -> restart the command preserving the input cursor without advancing (single mode: `--after <after>`, keeping the returned input cursor so unread messages are not skipped, rather than advancing to `cursor`/`messageCursor`; multi/group mode: pass all returned `<taskId>:<resumeAfter>` pairs from `targets`) without falling back to MCP polling when a terminal is available; `owner-stopped` -> one `black_gravity_status` on task `taskId`; `unknown-task`, `unknown-group` or `error` -> check the IDs/directory and fall back to `black_gravity_wait` / `black_gravity_group_wait`. For another `taskId` (e.g. `continuationTaskId`), append the ID to `black_gravity_health.waitCommand.argv`. If you use `black_gravity_wait` (`timeoutSeconds: 60`), continue with `nextCursor` while `ready` is false; notifications match real events (numbers are not percentages), and a wait timeout or cancellation does not end the task (use `black_gravity_cancel` for that). Events (`black_gravity_events`) report observable activity, not private reasoning; if `truncated` is true, report the loss of older events.

Verified data point, not a rule: on Claude Code 2.1.314, a background `Bash` call with `timeout: 1200000` let a 1000 s command finish with exit code 0, so `--timeout 1140` kept a 60 s margin there. Other versions may differ; confirm the deadline in the host.

## Compact delivery

Prefer `deliveryMode: "messages"` for ordinary delegations. `black_gravity_wait` delivers structured public questions, blockers and final excerpts with references; it does not send the detailed tool history to the main agent. Keep `nextCursor`, check `deliveryMode` and report losses flagged by `truncated`. A message may arrive with `ready: false`; answer the pertinent question and keep tracking. With `waitCommand` in the background, questions and blockers published in this mode end the command reporting the `sequence` in `cursor`, and a single call to `black_gravity_wait` with `after: cursor - 1` is enough to read the text. A message does not prove reading, execution, verification or human approval.

Use `events` when the user asks for detailed diagnostics. `black_gravity_events`, the result readers and the patch reader remain available when needed. When changing the mode with `black_gravity_set_delivery_mode`, restart at `after: 0`; event cursors and message cursors are different. Send `cursorMode` with the mode of the previous cursor; `cursorReset: true` reports an automatic restart when the caller changed the delivery. Omission keeps the legacy mode and resuming inherits the choice. Content is public output emitted by the CLI; do not extract private reasoning or use the message as an answer to a pending agy permission.
