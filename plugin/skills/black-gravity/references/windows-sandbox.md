# Windows sandbox and tests

Reference for the [core skill](../SKILL.md). Open it when using `black_gravity_test`, the sandbox policy or the portable Node runtime, or on LPAC failures.

## Windows sandbox permissions

- The user authorizes the global limits (in `auto`, validated `black_gravity_set_sandbox_policy` proposals are applied automatically; in `ask`, it requires human confirmation through an MCP form with the previous hash). Before selecting permissions, the agent calling the MCP, whether Codex or another client, must call `black_gravity_get_sandbox_policy`. It shows those limits and their `sha256`. On Windows, that agent uses in `black_gravity_test` only a `sandbox: { readPaths, writePaths, network, childProcesses, maxOutputChars }` contained within those limits. The caller may propose narrow, verified grants needed by the authorized task in tests. The Gemini delegated via `agy` cannot choose, authorize or change grants. Do not choose broad paths or presume the user's local paths.
- To change the global limit, call `black_gravity_set_sandbox_policy` with the current hash and the normalized proposal. In `auto` mode (default if unset), the validated proposal is applied automatically without a form; in `ask` mode, the MCP client must present the interactive form with the previous and proposed limits for human confirmation. The hash prevents a late response from replacing a different policy.
- Example proposal, with checked roots: `readRoots: ["<raiz-de-leitura-aprovada>"]`, `writeRoots: ["<raiz-de-escrita-aprovada>"]`, `network: false`, `childProcesses: true`, `maxOutputChars: 4000`. Then choose, for a test, only the subpaths needed. Never grant an entire disk.
- The policy and the selectors apply to the Windows LPAC executor. If `BRIDGE_TEST_EXECUTOR=agy` is active, an explicit selection is refused; omitting it keeps the legacy `agy` behavior. There is no automatic fallback to the host, nor any change to Codex/agy permissions.

## Tests in the sandbox

- For the Windows LPAC portable Node runtime, check `node plugin/server.mjs --windows-runtime-status` before preparing. This check is local, does not start MCP, does not discover `agy` and does not download files. On Windows x64, `node plugin/server.mjs --prepare-windows-runtime` explicitly downloads only the `node.exe`, `LICENSE` and `build.json` declared in the GitHub Release, checks size and SHA-256 and installs the private cache atomically. Startup, health and tests do not download files. To prepare through the npm package 0.8.0, use `npx --yes antigravity-mcp-bridge@0.8.0 --prepare-windows-runtime`. Do not pass a URL, hash or cache path through an MCP tool.
- Direct npm keeps `BRIDGE_WINDOWS_NODE_RUNTIME=system`; the plugin descriptor selects `portable`. Portable mode requires a valid cache and does not fall back to the system Node when the cache is missing or corrupted. `BRIDGE_WINDOWS_NODE_CACHE_DIRECTORY` is a trusted startup setting for sharing that cache. The Node 24.21.0 LPAC1 Windows x64 runtime, with base libuv 1.52.1 and only PR 5181 applied, is already published in an immutable Release and available for explicit preparation. The initial portable replacement of `process.execPath` and the adjacent `npm` requires Node 24 on the server host. The general Node >=24 requirement allows the server to start, but Node 25/26 hosts fail in eligible tests with `PORTABLE_NODE_HOST_UNSUPPORTED`.
- Keep `BRIDGE_WINDOWS_NODE_CACHE_DIRECTORY` outside projects. The bridge resolves the real paths and refuses overlap in both directions before querying models, queuing the task or copying files, even with `includePaths` or in `system` mode. A missing cache requires `--prepare-windows-runtime`; a corrupted, altered or unsafe cache is refused, by preparation as well, without automatic repair or removal. Before preparing again, a person must inspect the path and manually remove only the cache of the affected build; then run `--prepare-windows-runtime`. In caches under synchronization such as OneDrive, tolerance of an extra or transient link count (`nlink`) is restricted exclusively to reading assets with a trusted descriptor and pinned size and SHA-256, to staging the portable Node source with `expectedSha256`, and to the portable Node preparation lock (preserving identical `device`, `inode` and `size` and a checked exact nonce/payload, releasing with `unlink` only the process's own entry to preserve aliases). Hash, size, file identity, reparse tags and directory layout remain strictly mandatory; altered content is refused and aliases are not modified. Runtime destinations, generic executables and ACL grants still require a single link. `StateStore` has no generic support for cloud storage.
- Use `black_gravity_test` with the command split into `executable` and `args`, the current hash, an adequate deadline and, on Windows, an already approved sandbox selection. The default executor on Windows is owned by the bridge and uses AppContainer/LPAC; it needs neither Docker nor UAC configuration. Do not work around a refusal by running on the host.
- On Windows, use an `.exe` or `npm`/`npm.cmd`. The bridge prepares verified `node.exe` and `npm-cli.js`; arbitrary `.cmd`/`.bat` files are not compatible. The .NET Framework compiler already present on Windows is required for the controller.
- Node/npm tests and direct git commands on Windows automatically prepare the Git for Windows discovered in `PATH`, resolving `cmd` and `bin` launchers to the native executable in `ucrt64/bin` or `mingw64/bin` when there is a known layout. Native executables and standalone installations are preserved; invalid or unsafe known layouts are refused. Exclusively PE binaries, DLLs and public helpers are copied to a read-only runtime with single links at the destination; source files may contain hardlinks in the original installation, but it receives no ACLs or grants. The skill must not ask for a grant in Program Files or a manual copy for hardlinked Git. `PATH` preserves exclusively the runtime directories and the exact `System32`; `GIT_EXEC_PATH` points to the directory in the runtime alias, the global configuration points to a missing file in scratch and `GIT_CONFIG_NOSYSTEM=1` and `GIT_TERMINAL_PROMPT=0` are set. Injected entries of `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*`, `GIT_CONFIG_VALUE_*` and `GIT_CONFIG_PARAMETERS` are removed, and the protected command configuration defines `safe.directory` restricted solely to the exact list of verified repositories present in the copy at the start of the run: empty reset (`VALUE_0=''`), root of the verified copy alias (`VALUE_1`) and roots of the descendant repositories with a verified `.git` directory inside the copy (`VALUE_2..N`), without the `*` wildcard and without trusting anything outside the copy, keeping Git's normal checks for new repositories created after admission. There is no inheritance of `.gitconfig`, credentials or keys, nor any download of Git. The optional absence of Git does not prevent Node/npm tests without Git (commands that require Git fail if it is absent), and the copied files count toward the mandatory copy limits, without extra authorizations for the installation or fallback to the host.
- New temporary repositories created in the sandbox use the `reftable` format (`GIT_DEFAULT_REF_FORMAT=reftable`), which must be supported by the installed Git. The setting does not convert existing repositories or change the host's Git. The traditional `files` backend and Git versions without reftable support have a limitation in LPAC when querying private parent directories; this selection does not loosen file system isolation, private parents remain denied, with no new metadata grants, no UAC and no fallback to the host.
- When Git is prepared, the controller checks access to Null through a fixed path. The default LPAC rule, when sufficient, avoids ACL writes and `WRITE_DAC`. If needed and permitted by the current token, it records a temporary grant only for the run's SID before applying it. Private jobs and v3 leases make it possible to verify termination and recover grants and aliases. Lack of access or inconclusive cleanup produces an error; do not request elevation or widen permissions to work around it.

- Node 24 or later remains a server requirement, but does not guarantee every subprocess in LPAC. On Node 24.14.1/libuv 1.51, `child_process.spawnSync` with default stdin/stdout/stderr pipes times out with exit code 124; a child that passes with `stdio: "inherit"` or a real npm cycle does not prove general compatibility. The published portable runtime uses PR 5181 and passed the LPAC `spawnSync` regression with captured default pipes and the 22 isolation and lifecycle tests, with no failures or skips. This validation applies to the Node 24.21.0 LPAC1 Windows x64 build. Do not swap the pipes for inherited stdio to declare the failure resolved. A timeout is a failure and cannot support integration.
- The tool returns a continuation with another `taskId`. Track that ID and do the review/integration of the most recent task. Examine `source: "windows-executor"` and `sandbox: "windows-lpac"` on Windows, or `source: "agy-tool"` and `sandbox: "agy-native-requested"` on the legacy path, as well as exit code, output, selection, policy hash and `stale`. Do not attribute a real run to `client-reported` or to Gemini's narrative.
- The Windows controller needs three free letters between `D:` and `Z:` for temporary aliases, on two levels, of the copy, runtime and scratch. It checks the identity and the removal of the aliases, including when recovering an interrupted run. If the removal is not proven, it preserves the record for recovery and there is no verified success. The names are visible in the current logon and do not create a persistent mount, a grant at the volume root or a UAC request.
- `retries: 0` keeps the default without automatic correction. Only ask for up to 3 additional corrections when authorized by the task. On a Windows failure, an optional correction by `agy` does not receive and cannot change the policy; report only the counters returned by the CLI and keep absences as `null`. The known local run records zero model tokens.
- `TEST_FAILED` preserves the observed failure. Run the commands again after changing the files; old records do not validate the current patch. Untrusted model output is not a receipt; use the evidence observed by the executor. The Windows evidence covers a new run and process recovery, but does not prove a physical reboot. A cleanup failure prevents verified success and blocks use of the grant until recovery; a power interruption may require that later recovery.
- After fixing an infrastructure failure of the local Windows executor, repeat `black_gravity_test` on the latest taskId with the current preview. The bridge reconciles the leases before creating another attempt and preserves the previous failure. Runs still active or an inconclusive recovery prevent the repetition. This path does not release tests of CLI tasks that were cancelled, expired or failed because of the model; do not change their states to force the resume.
