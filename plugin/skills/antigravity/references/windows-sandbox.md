# Windows sandbox and tests

Reference for the [core skill](../SKILL.md). Open it when using `antigravity_test`, the sandbox policy or the portable Node runtime, or on LPAC failures.

## Permissões do sandbox Windows

- A pessoa usuária autoriza os limites globais (em `auto`, propostas validadas de `antigravity_set_sandbox_policy` são aplicadas automaticamente; em `ask`, exige confirmação humana por formulário MCP com o hash anterior). Antes de selecionar permissões, o agente que chama o MCP, seja o Codex ou outro cliente, deve chamar `antigravity_get_sandbox_policy`. Ela mostra esses limites e seu `sha256`. No Windows, esse agente usa em `antigravity_test` somente `sandbox: { readPaths, writePaths, network, childProcesses, maxOutputChars }` contido nesses limites. O chamador pode propor concessões estreitas e verificadas necessárias à tarefa autorizada nos testes. O Gemini delegado via `agy` não pode escolher, autorizar nem alterar concessões. Não escolha caminhos amplos nem presuma caminhos locais do usuário.
- Para mudar o limite global, chame `antigravity_set_sandbox_policy` com o hash atual e a proposta normalizada. No modo `auto` (padrão se unset), a proposta validada é aplicada automaticamente sem formulário; no modo `ask`, o cliente MCP deve apresentar o formulário interativo com os limites anteriores e propostos para confirmação humana. O hash impede que uma resposta tardia substitua uma política diferente.
- Exemplo de proposta, com raízes conferidas: `readRoots: ["<raiz-de-leitura-aprovada>"]`, `writeRoots: ["<raiz-de-escrita-aprovada>"]`, `network: false`, `childProcesses: true`, `maxOutputChars: 4000`. Depois escolha, para um teste, apenas subcaminhos necessários. Nunca conceda um disco inteiro.
- A política e os seletores valem para o executor Windows LPAC. Se `BRIDGE_TEST_EXECUTOR=agy` estiver ativo, uma seleção explícita é recusada; omiti-la mantém o comportamento legado do `agy`. Não há fallback automático ao host, nem alteração de permissões Codex/agy.

## Testes no sandbox

- Para o runtime Node portátil Windows LPAC, consulte `node plugin/server.mjs --windows-runtime-status` antes de preparar. Essa consulta é local, não inicia MCP, não descobre `agy` e não baixa arquivos. Em Windows x64, `node plugin/server.mjs --prepare-windows-runtime` baixa explicitamente somente `node.exe`, `LICENSE` e `build.json` declarados no GitHub Release, confere tamanho e SHA-256 e instala o cache privado de modo atômico. Inicialização, saúde e testes não baixam arquivos. Para preparar pelo pacote npm 0.8.0, use `npx --yes antigravity-mcp-bridge@0.8.0 --prepare-windows-runtime`. Não passe URL, hash ou caminho de cache por uma ferramenta MCP.
- O npm direto mantém `BRIDGE_WINDOWS_NODE_RUNTIME=system`; o descritor do plugin seleciona `portable`. O modo portátil requer cache válido e não volta ao Node do sistema quando ele está ausente ou corrompido. `BRIDGE_WINDOWS_NODE_CACHE_DIRECTORY` é uma configuração confiável de inicialização para compartilhar esse cache. O runtime Node 24.21.0 LPAC1 Windows x64, com libuv base 1.52.1 e somente o PR 5181 aplicado, já está publicado em Release imutável e disponível para preparação explícita. A substituição portátil inicial de `process.execPath` e do `npm` adjacente exige Node 24 no host do servidor. O requisito geral Node >=24 permite iniciar o servidor, mas hosts Node 25/26 falham em testes elegíveis com `PORTABLE_NODE_HOST_UNSUPPORTED`.
- Mantenha `BRIDGE_WINDOWS_NODE_CACHE_DIRECTORY` fora dos projetos. O bridge resolve os caminhos reais e recusa sobreposição em ambas as direções antes de consultar modelos, enfileirar a tarefa ou copiar arquivos, mesmo com `includePaths` ou no modo `system`. Cache ausente exige `--prepare-windows-runtime`; cache corrompido, alterado ou inseguro é recusado também pela preparação, sem reparo nem remoção automática. Antes de preparar novamente, uma pessoa deve inspecionar o caminho e remover manualmente somente o cache do build afetado; depois, executar `--prepare-windows-runtime`. Em caches sob sincronização como OneDrive, a tolerância a contagem extra ou transitória de links (`nlink`) restringe-se exclusivamente à leitura de assets com descritor confiável, tamanho e SHA-256 fixados, ao staging da fonte do Node portátil com `expectedSha256`, e ao lock de preparação do Node portátil (preservando `device`, `inode` e `size` idênticos e nonce/payload exato conferido, liberando com `unlink` apenas a entrada do próprio processo para preservar aliases). Hash, tamanho, identidade de arquivo, marcas de reparse e layout de diretório permanecem estritamente obrigatórios; conteúdo alterado é recusado e aliases não são modificados. Destinos de runtime, executáveis genéricos e concessões de ACL continuam exigindo link único. O `StateStore` não possui suporte genérico a armazenamento em nuvem.
- Use `antigravity_test` com comando separado em `executable` e `args`, hash atual, prazo adequado e, no Windows, uma seleção de sandbox já aprovada. O executor padrão no Windows é propriedade do bridge e usa AppContainer/LPAC; ele não precisa de Docker nem de configuração UAC. Não contorne uma recusa com execução no host.
- No Windows, use um `.exe` ou `npm`/`npm.cmd`. O bridge prepara `node.exe` e `npm-cli.js` verificados; arquivos `.cmd`/`.bat` arbitrários não são compatíveis. O compilador .NET Framework existente no Windows é necessário para o controlador.
- Testes Node/npm e comandos git diretos no Windows preparam automaticamente o Git for Windows descoberto no `PATH`, resolvendo launchers de `cmd` e `bin` para o executável nativo em `ucrt64/bin` ou `mingw64/bin` quando há um layout conhecido. Executáveis nativos e instalações standalone são preservados; layouts conhecidos inválidos ou inseguros são recusados. Copiam-se exclusivamente binários PE, DLLs e helpers públicos para um runtime somente leitura com links únicos no destino; arquivos de origem podem conter hardlinks na instalação original, mas ela não recebe ACLs nem concessões. A skill não deve pedir concessão em Program Files nem cópia manual para Git hardlinked. O `PATH` preserva exclusivamente os diretórios do runtime e o `System32` exato; `GIT_EXEC_PATH` aponta para o diretório no alias do runtime, a configuração global aponta para arquivo ausente em scratch e definem-se `GIT_CONFIG_NOSYSTEM=1` e `GIT_TERMINAL_PROMPT=0`. Entradas injetadas de `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*`, `GIT_CONFIG_VALUE_*` e `GIT_CONFIG_PARAMETERS` são removidas, e a configuração protegida de comando define `safe.directory` restrita unicamente à lista exata dos depósitos verificados presentes na cópia no início da execução: reset vazio (`VALUE_0=''`), raiz do alias da cópia verificada (`VALUE_1`) e raízes dos depósitos descendentes com diretório `.git` verificado dentro da cópia (`VALUE_2..N`), sem wildcard `*` e sem confiar fora da cópia, mantendo checagens normais do Git para novos depósitos criados após a admissão. Não há herança de `.gitconfig`, credenciais ou chaves, nem download do Git. A ausência opcional de Git não impede testes Node/npm sem Git (comandos que exigem Git falham se ausente), e os arquivos copiados contam para os limites obrigatórios de cópia, sem autorizações extras para a instalação nem fallback ao host.
- Novos repositórios temporários criados no sandbox usam o formato `reftable` (`GIT_DEFAULT_REF_FORMAT=reftable`), que deve ser suportado pelo Git instalado. A configuração não converte repositórios existentes nem altera o Git do host. O backend tradicional `files` e versões do Git sem suporte a reftable possuem limitação no LPAC ao consultar diretórios pais privados; essa seleção não afrouxa o isolamento do sistema de arquivos, pais privados continuam negados, sem novas concessões de metadados, sem UAC e sem fallback ao host.
- Quando o Git está preparado, o controlador consulta o acesso ao Null por um caminho fixo. A regra padrão de LPAC, quando suficiente, dispensa escrita de ACL e `WRITE_DAC`. Se necessário e permitido pelo token atual, registra uma concessão temporária somente para o SID da execução antes de aplicá-la. Jobs privados e leases v3 permitem verificar o término e recuperar concessões e aliases. Falta de acesso ou limpeza inconclusiva produz erro; não solicite elevação nem amplie permissões para contorná-lo.

- Node 24 ou mais recente continua sendo requisito do servidor, mas não garante todos os subprocessos no LPAC. No Node 24.14.1/libuv 1.51, `child_process.spawnSync` com pipes padrão de stdin/stdout/stderr expira com exit code 124; um filho que passe com `stdio: "inherit"` ou um ciclo real do npm não prova compatibilidade geral. O runtime portátil publicado usa o PR 5181 e passou pela regressão LPAC de `spawnSync` com pipes padrão capturados e pelos 22 testes de isolamento e ciclo de vida, sem falhas nem skips. Essa validação se aplica ao build Node 24.21.0 LPAC1 Windows x64. Não troque os pipes por stdio herdado para declarar a falha resolvida. Um timeout é falha e não pode fundamentar integração.
- A ferramenta devolve uma continuação com outro `taskId`. Acompanhe esse ID e faça a revisão/integração da tarefa mais recente. Examine `source: "windows-executor"` e `sandbox: "windows-lpac"` no Windows, ou `source: "agy-tool"` e `sandbox: "agy-native-requested"` no caminho legado, além de exit code, saída, seleção, hash da política e `stale`. Não atribua execução real a `client-reported` ou à narrativa do Gemini.
- O controlador Windows precisa de três letras livres entre `D:` e `Z:` para aliases temporários, em dois níveis, da cópia, runtime e scratch. Ele confere a identidade e a remoção dos aliases, inclusive na recuperação de execução interrompida. Se a remoção não for comprovada, preserva o registro para recuperação e não há sucesso verificado. Os nomes são visíveis no logon atual e não criam mount persistente, concessão na raiz do volume ou pedido de UAC.
- `retries: 0` preserva o padrão sem correção automática. Só peça até 3 correções adicionais quando autorizadas pela tarefa. Em falha Windows, uma correção opcional pelo `agy` não recebe nem pode mudar a política; informe apenas os contadores devolvidos pelo CLI e mantenha ausências como `null`. A execução local conhecida registra zero tokens de modelo.
- `TEST_FAILED` preserva a falha observada. Rode novamente os comandos depois de mudar os arquivos; registros antigos não validam o patch atual. Saída não confiável do modelo não é recibo; use a evidência observada pelo executor. A evidência Windows abrange nova execução e recuperação de processo, mas não prova reinicialização física. Falha de limpeza impede sucesso verificado e bloqueia o uso da concessão até recuperação; interrupção de energia pode exigir essa recuperação posterior.
- Após corrigir uma falha de infraestrutura do executor local Windows, repita `antigravity_test` no último taskId com a prévia atual. O bridge reconcilia as leases antes de criar outra tentativa e preserva a falha anterior. Execuções ainda ativas ou recuperação inconclusiva impedem a repetição. Esse caminho não libera testes de tarefas do CLI canceladas, expiradas ou com falha do modelo; não altere seus estados para forçar a retomada.
