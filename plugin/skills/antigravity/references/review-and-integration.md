# Review, evidence and integration details

Reference for the [core skill](../SKILL.md). Open it when dealing with integration refusals, encoding errors or warnings, chunked reads of results and patches, or `integrationApproval.available` false.

After `completed`, call `antigravity_preview`, present `summary` and `fileSummaries` (A/M/D, added/removed lines and binaries), review the whole patch and run the relevant tests in the copy. For files that contain non-UTF-8 content, declare them as `binary` in `.gitattributes`; text changes that do not round-trip through UTF-8 fail with `UNSUPPORTED_PATCH_ENCODING` to prevent patch corruption, and a write task whose copy already has such files is refused before the CLI starts with `UNSUPPORTED_TEXT_ENCODING`, which lists the files. Also present `encodingWarnings`, when there are any: a new UTF-16 file enters the patch as binary. Record the commands actually run with `antigravity_record_test`, using the current hash and the output without secrets. These records are client reports, not independent verification by the bridge. Present failures and `stale: true` records; do not use them as valid evidence for the current patch. A CLI `SUCCESS` result does not replace this verification. Call `antigravity_integrate` with the `taskId` and the `sha256` of the preview. In `auto` mode (default if unset), the bridge authorizes verified integration automatically, skipping interactive human confirmation forms. In `ask` mode, the server requires an interactive form (**MCP form elicitation**) with `accept` and `confirm: true`, even for previously remembered roots or legacy configured roots (the remember checkbox was removed from the form). If `integrationApproval.available` is false in `ask` mode, report that the current MCP client does not support approval forms. Do not bypass the confirmation by applying the patch another way without the user's authorization. Report failures and limitations accurately.

## Chunked reading

- Track `antigravity_result` with `includeResult: false`. After `ready: true`, read only the needed chunks through `antigravity_read_result`, keeping `contentSha256` on the following pages.
- Request `antigravity_preview` with `includePatch: false`. Read the diff of each changed file through `antigravity_read_patch`, with the full hash and the path given in the preview. Follow `nextOffset` until `hasMore: false`; do not declare the review complete if chunks remain.
- If there is `REVIEW_CHANGED` or `CONTENT_CHANGED`, get a new preview/first page and restart the affected review. Never concatenate pages from different versions. Do not calculate offsets manually or assume that the chunk received is all of the content.

## Evidence before integration

- Define `acceptanceCriteria` in `antigravity_run` before implementation, covering every explicit requirement. Use file checks when applicable and review criteria for behaviors that require interpretation. Resuming keeps the original criteria.
- Read the actual artifacts and compare each requirement with the result. For each criterion, send `antigravity_verify` a review with file, line, literal quote and explanation. Do not invent quotes, outputs or command runs. Classify lack of proof as `unverified` and defects as `failed`.
- `completed` and `SUCCESS` indicate that the run ended. Report a requirement as met only with pertinent evidence. Also check tests, observable effects, uncovered requirements and limitations; a text search or a correct quote does not prove the whole behavior.
- Without criteria, a complete review or a current verification, the server blocks integration. If the patch or the evidence changes, review and verify again. Integration is governed by the active mode: in `auto`, verified patches are authorized automatically; in `ask`, human confirmation through an MCP form is always indispensable.
